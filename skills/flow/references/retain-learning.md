# Retaining useful learning

Read before a learning write. Honor no-save instructions and the host's permissions and persistence rules. Do not assume writable memory or skill proposals exist on every platform.

## Decide whether the learning is worth keeping

For each candidate, identify:

- **Observation:** what happened, with a relevant check, artifact, user correction, or source.
- **Implication:** the specific step, ordering, branch, or constraint to change.
- **Scope:** which tasks, people, projects, or tool conditions it applies to.
- **Evidence status:** observed on a real task, observed in a simulation, or proposed and untested.
- **Uncertainty:** what remains unverified or may change.

Keep only information likely to improve future work. Omit generic advice, unsupported causal claims, secrets, unrelated personal details, and transient failures without a reusable implication. User silence is not approval; one successful run is not proof of superiority.

## Choose the destination

| Learning | Action |
|---|---|
| Repeatable task method | Find and improve an existing matching flow; create a distinct skill only when useful and materially different. |
| Correction to a specialist method | Patch the narrowest appropriate skill or reference; edit the operative instructions rather than merely appending a lesson. |
| Explicit durable preference or verified project decision | Write to an authorized memory/context mechanism with source, date, and scope. Do not turn an inference into a user fact. |
| Researched domain knowledge | Retain attributed, dated references with the appropriate domain skill or project; include freshness limits. |
| Execution checkpoint | Keep in the task/project record, separate from reusable operating instructions. |
| Unexecuted flow explicitly requested for saving | Save as a draft with pending validation. |
| One-off task, simulation, or no substantive learning | Do not create real user memories or production skills by default. Keep only a useful task/test record. |

A request to “save this flow” does not itself make its instructions tested. A failed tool call does not establish that the service is universally unavailable. Avoid recording either as stronger evidence than it is.

## Save or improve a skill

1. Read the existing skill before changing it and check for overlap elsewhere.
2. Extract the procedure that actually ran, including useful corrections. Parameterize audience, inputs, format, and constraints; remove one-off private details.
3. Prefer `flow-<task-type>` for a new flow, but preserve established local names and search descriptions as well as prefixes.
4. Use the linked saved-flow template. Include trigger/scope, required inputs, steps with purpose and done conditions, genuine gates, dependencies/fallbacks, checks, and honest validation status.
5. Keep shared rules in the appropriate specialist skill. Do not duplicate brand guidance or require Flow recursively. If an optional specialist skill is absent, use a supported alternative; if it is essential, state the missing dependency.
6. Use the host's skill-creator process, validate structure, and forward-test when justified and authorized. Passing structural validation is not a behavioral evaluation.
7. Count only observed runs, separating real and simulated use. Record dated lessons only when they change the procedure. Preserve relevant prior evidence without inflating validation claims.
8. Complete the host's durable save, including repository synchronization if required. Verify its result.

## Verify and report persistence

A file written locally, a proposed skill card, and a durable saved skill are different states. Use supported operations and report the actual state. Do not claim that memory was updated through a search-only tool or that a background process will capture it.

If saving fails, retain useful local work where possible and report what remains unsaved. Offer a proposed entry only when it helps the user recover. Never broaden permissions or bypass access controls to force persistence.

Keep retention proportionate. Deliver the requested work and briefly state the useful change saved; do not let optional learning become a second large project.
